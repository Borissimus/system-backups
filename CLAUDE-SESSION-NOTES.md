# Стан відновлення системи — нотатки для нової сесії Claude

Якщо ти читаєш це в новому чаті: попередня сесія працювала з Live USB, чия
історія (`~/.claude`) живе на ефемерному `/cow` overlay і зникає при
перезавантаженні. Це не втрата даних — сам бекап і скрипти на постійному
диску `backup_img` цілі. Нижче — все, що треба знати, щоб продовжити.

## Ситуація

- Працюємо з Ubuntu 24.04 Live USB (UEFI), overlay-root на `/cow`.
- Диск бекапу: `/dev/sda` (2TB), змонтований у `/media/ubuntu/backup_img`.
  Містить: `nvme0n1-full.img` (повний dd-образ, не використовуємо в цьому
  сценарії), `home_cp/` (копія домашньої директорії, **ігноруємо** за
  вказівкою користувача), `system-backups/` (те, що використовуємо).
- Цільовий диск: `/dev/nvme0n1` — Micron 2400 NVMe 512GB
  (модель `2400 NVMe Micron 512GB`, серійний `23103F15478F`,
  `512110190592` байт). Це **єдиний** NVMe на машині, раніше перевірений
  SMART-health — диск здоровий (9% Percentage Used, 0 помилок).
- Оригінальна система була на диску ~1TB, але фактично займала
  ~275.5 GiB (`root` snapshot) — тому 512GB SSD достатньо для повного
  відновлення (тестовий сценарій з RECOVERY.md, LVM пересоздається заново,
  а не клонується 1:1).

## Що вже зроблено

1. Встановлено інструменти: `smartmontools`, `nvme-cli`, `restic`,
   `shellcheck` (через `sudo apt install`).
2. Прочитано `/media/ubuntu/backup_img/system-backups/RECOVERY.md` повністю
   — це основне джерело правди для процедури відновлення.
3. Перевірено структуру `system-backups/`:
   - `restic/` — репозиторій restic (5308 pack-файлів на момент останньої
     повної перевірки 2026-09-10, `restic check --read-data` пройшла без
     помилок).
   - `recovery-metadata/` — `blkid.txt`, `nvme0n1.sfdisk`, `nvme0n1.gpt`,
     `nvme0n1p3-luks-header.img`, `pvs.txt`, `vgs.txt`, `lvs.txt`,
     `ubuntu-vg.conf`, `lsblk.txt` — всі на місці.
   - Три snapshot'и в restic: `system-root`, `system-boot`,
     `recovery-metadata` (усі від 2026-09-08).
4. Написано й перевірено (`bash -n` + `shellcheck -S warning`, 0
   зауважень) два скрипти, покладено в
   `/media/ubuntu/backup_img/system-backups/`:

   - **`restore-system.sh`** — повне відновлення на новий диск.
     Режими: `--dry-run` (нічого не змінює, тільки перевіряє) і звичайний
     (реально виконує відновлення). Що робить: перевіряє структуру бекапу
     й інструменти → просить пароль restic (одноразово, `read -rs`,
     `export RESTIC_PASSWORD`, `unset` у trap на виході) → перевіряє
     snapshots і розмір даних (`restic stats ... restore-size`) → шукає
     диски-кандидати (виключає диск бекапу й Live USB) → вимагає ввести
     точний шлях диска двічі (вибір + фінальне підтвердження) → чистить і
     розбиває диск (`sgdisk`: ESP 1G / boot 2G / LVM решта) → відновлює
     LUKS header з `recovery-metadata` → **тут `cryptsetup open` запитує
     LUKS-пароль вручну** → створює LVM (`lvcreate -l 90%FREE`, тобто LV
     сама підлаштовується під розмір будь-якого диска) → форматує розділи
     з UUID, взятими з `blkid.txt` → `restic restore` + `rsync` для root і
     boot → править `fstab` → `chroot` + `update-initramfs` +
     `grub-install` + `update-grub` + перевірка `efibootmgr` (з fallback
     на `--removable`) → розмонтовує, закриває LUKS.

   - **`backup-system.sh`** — майбутні інкрементні бекапи. Запускається
     НЕ з Live USB, а на вже встановленій системі. Автовизначає
     VG/LV/LUKS-розділ поточного `/`, рахує розмір LVM snapshot динамічно
     (`min(вільне_у_VG-1, 20%_від_LV, мінімум 5G)`), оновлює
     `recovery-metadata` наживо, створює LVM snapshot кореня, одним
     запуском (`restic backup` тричі підряд) відправляє `system-root`,
     `system-boot`, `recovery-metadata` в **той самий** repo з тегом
     `run-<timestamp>` — restic сам по собі дедуплікує і зберігає лише
     зміни відносно попередніх снапшотів, тому додаткової "інкрементності"
     писати не треба. Прибирає snapshot. Опційно `--prune` для
     retention (`--keep-daily 7 --keep-weekly 4 --keep-monthly 6`).
     Пароль restic — так само вручну, одноразово за запуск.

## Спроба №1 відновлення (2026-09-16, ~18:12) — перервана

Користувач запустив `restore-system.sh` реально (без `--dry-run`). Дійшло
до кроку `sgdisk` (партиціонування `/dev/nvme0n1` — ESP/boot/LVM-розділи
створені успішно), потім впало на
`cryptsetup luksHeaderRestore /dev/nvme0n1p3 --header-backup-file ...`:
cryptsetup сам питає підтвердження і вимагає ввести **рівно** `YES`
великими літерами (не `yes`, не `Yes`) — користувач ввів `yes` малими,
cryptsetup відмовився, скрипт впав з кодом 1.

**Стан диска після падіння:** розділи `nvme0n1p1/p2/p3` вже існують, LUKS
не відновлено, LVM не створено, процес не запущений. Безпечно перезапускати
скрипт з нуля — він сам перечистить і перестворить розділи (`wipefs` +
`sgdisk --zap-all` на початку кроку 6).

**Наступного разу:** при тому самому запиті ввести `YES` великими
літерами.

## Спроба №2 (2026-09-16, ~18:2x) — перервана на форматуванні ESP

Дійшло далі: LUKS header відновлено (з `YES`), LVM створено (PV/VG/LV),
але впало на `mkfs.fat -F 32 -i "$ESP_UUID_NODASH" "$ESP"`:
"Volume ID must be a hexadecimal number".

**Корінна причина — реальний баг у скрипті** (рядки ~271-273, до фіксу):
`grep -oP 'UUID="\K[^"]+'` матчив і `UUID="..."`, і `PARTUUID="..."` (бо
`"UUID="` — підрядок `"PARTUUID="`), тому для `nvme0n1p1`/`nvme0n1p2` (у
яких в blkid.txt є обидва поля) `$ESP_UUID`/`$BOOT_UUID` виходили
багаторядковими (UUID + PARTUUID зліплені), що ламало і `mkfs.fat -i`, і
потенційно `mkfs.ext4 -U` для BOOT.

**Виправлено** в `restore-system.sh`: regex тепер
`grep -oP '(?<!PART)UUID="\K[^"]+'` (негативний lookbehind виключає
PARTUUID). Перевірено вручну на `blkid.txt` — тепер `ESP_UUID_NODASH`
= `157127FF` (валідні 8 hex-символів), `BOOT_UUID`/`ROOT_UUID` — чисті
однорядкові UUID. `bash -n` + `shellcheck -S warning` — чисто.

**Також додано (за проханням користувача — "декілька шансів" замість
миттєвого падіння):** retry-цикли (по 3 спроби) на трьох інтерактивних
місцях, де найімовірніша людська помилка:
1. Введення пароля restic (крок 3, читання snapshots).
2. `cryptsetup luksHeaderRestore` (крок 7 — власне підтвердження
   cryptsetup "YES").
3. `cryptsetup open` (пароль LUKS, крок 7).

Інші кроки (mkfs, restic restore, chroot/grub) навмисно без retry —
там або баг, або апаратна проблема, а не помилка вводу, і повторювати
їх автоматично небезпечно/безглуздо.

**Стан диска після падіння спроби №2:** розділи створені, LUKS відкритий
як `/dev/mapper/cryptroot`, LVM (`ubuntu-vg`/`ubuntu-lv`) створено й
активовано, файлові системи ще НЕ відформатовані. Перед повторним
запуском скрипт сам робить `cryptsetup close` + `vgchange -an` на
початку кроку 6, тому безпечно просто перезапустити з нуля.

## Спроба №3 (2026-09-16, ~18:2x) — перервана на wipefs "resource busy"

Дійшла до `wipefs -a "$DISK"` (крок 6) і впала:
`wipefs: error: /dev/nvme0n1: probing initialization failed: Device or
resource busy`.

**Корінна причина #1 (реальний баг скрипту):** порядок деактивації був
переплутаний — `cryptsetup close "$CRYPT_NAME"` викликався **до**
`vgchange -an "$VG_NAME"`. Поки LV ще активна на cryptroot, close мовчки
провалюється (`|| true`), LUKS-мапінг лишається відкритим і тримає
`/dev/nvme0n1p3` зайнятим для wipefs/sgdisk. **Виправлено**: тепер
спершу `vgchange -an`, потім `cryptsetup close`, у циклі (5 спроб) з
перевіркою `/sys/class/block/<part>/holders` і примусовим
`dmsetup remove -f` як останнім кроком.

**Корінна причина #2 (специфіка Live-середовища, не баг скрипту як
такого):** на цьому Ubuntu Desktop Live USB у фоні працює
**`subiquity-server`** (`snap.ubuntu-desktop-bootstrap.subiquity-server`
— сервіс інсталятора, ще з завантаження системи о 17:09) — він постійно
пробує/сканує диски (виявлення існуючих ОС для інсталятора) і, побачивши
PV `cryptroot`, кожного разу автоматично реактивовує `ubuntu-vg`/
`ubuntu-lv` менш ніж за секунду після нашої деактивації. Це діагностовано
наживо через `journalctl` (команди `dmsetup info ... PWD=.../subiquity`
запущені від `root` одразу після кожного `dmsetup remove`), не udisks2 і
не класичний udev pvscan (обидва перевірено й виключено окремо).
`auto_activation_volume_list = []` у `/etc/lvm/lvm.conf` тут НЕ рятує,
бо subiquity, судячи з усього, викликає активацію напряму
(`vgchange -ay`/еквівалент), а не через `pvscan --cache --activate ay`,
який єдиний читає цей список.

**Виправлено:** в `restore-system.sh` на початку кроку 6 тепер
`snap stop ubuntu-desktop-bootstrap.subiquity-server` (best-effort, якщо
`snap` взагалі є) — перевірено вручну: після зупинки LV стабільно
лишається неактивною (перевірено з опитуванням 6+ секунд), `cryptsetup
close` і `wipefs` більше не блокуються.

**Побічний ефект під час діагностики:** на цій Live-сесії також змінено
`/etc/lvm/lvm.conf` (`auto_activation_volume_list = []`) і замасковано
`udisks2.service` (`systemctl mask`) — обидва зміни стосуються ЛИШЕ
поточної ефемерної Live-сесії (зникнуть при перезавантаженні), жодного
відношення до цільової системи чи бекапу не мають. Залишені як є (не
шкодять, udisks2 автомонтування на Live USB тут не потрібне).

**Стан диска на момент фіксу:** повністю вільний — `dmsetup ls` порожній,
holders на `nvme0n1p3` порожні, LVM/LUKS закрито вручну в правильному
порядку. Розділи (`p1/p2/p3`) з попередніх спроб лишаються на диску, але
скрипт сам робить `wipefs -a` + `sgdisk --zap-all` на початку кроку 6,
тому це не проблема.

## Журнал прогресу і resume (2026-09-17)

За проханням користувача `restore-system.sh` тепер вміє продовжувати
з місця обриву замість повного перезапуску:

- Прогрес пишеться у `.restore-progress` (поруч зі скриптом, той самий
  каталог `system-backups/`) — по одному кроку на рядок: `wipe_partition`,
  `luks_header_restore`, `luks_open`, `lvm_create`, `format_filesystems`,
  `mount_targets`, `restore_root`, `restore_boot`, `fstab_fixup`,
  `chroot_grub`.
- Звичайний повторний запуск (`sudo bash restore-system.sh`, той самий
  рядок) сам пропускає вже пройдені кроки і продовжує з провального
  місця — нічого спеціально вказувати не треба.
- Для кожного кроку є **live-перевірка** (не просто довіра журналу):
  якщо реальний стан диска розійшовся з журналом (наприклад, користувач
  вручну щось поправив між запусками), крок і все після нього
  автоматично забуваються й виконуються заново.
- При падінні (`set -e`) `cleanup()`-trap тепер друкує **конкретну
  підказку під конкретний крок** (напр. для `luks_header_restore` —
  нагадування про `YES` великими літерами; для `restore_root` —
  перевірити вільне місце) і показує команди:
  - `sudo bash restore-system.sh --status` — які кроки вже виконано.
  - `sudo bash restore-system.sh --retry-step=NAME` — примусово
    повторити конкретний крок (і все після нього), якщо користувач
    щось поправив вручну і хоче форсувати перевиконання.
  - `sudo bash restore-system.sh --reset` — забути весь прогрес,
    почати зовсім спочатку (включно з wipe диска).
- Синтаксис (`bash -n`) і `shellcheck -S warning` — чисто. Логіку
  журналу (`step_done`/`mark_done`/`forget_from`/`step_done_verified`)
  протестовано ізольовано поза реальним диском — коректно пропускає
  зроблене, виявляє "застарілі" записи й відкочується по
  `--retry-step`.
- **Побічний ефект**: файл `.restore-progress` тепер лежить у
  `system-backups/` після кожного реального запуску — це нешкідливий
  текстовий журнал (просто список назв кроків), можна ігнорувати або
  видалити (`--reset` робить це автоматично).

## Аудит backup-system.sh (2026-09-17, поки restore біжив у фоні)

Користувач хвилювався: "враховуй наявні бекапи, щоб не дублювати все
кожного разу — в цьому і була суть", плюс повідомив, що на ОРИГІНАЛЬНІЙ
системі (не цільовій) вільно ~200 GiB на LV для snapshot'ів. Пояснення
для майбутньої сесії: `backup-system.sh` вже за задумом НЕ дублює дані —
restic сам content-addressed (дедуплікація на рівні чанків незалежно від
файлу/дати), а LVM snapshot — лише консистентна точка в часі (COW), не
повна копія. Але сам скрипт ніколи не тестувався на реальній системі, і
аудит вживу (на змонтованому цільовому LVM під час restore) знайшов
**два реальні баги, через які скрипт узагалі ніколи не запрацював би**:

1. **Визначення VG/LV для `/` було непрацездатним.** Код робив
   `readlink -f` на `/dev/mapper/ubuntu--vg-ubuntu--lv` (дає `/dev/dm-N`)
   і порівнював це з `lv_path`, який `lvs` завжди звітує у форматі
   `/dev/VG/LV` (символічне посилання) — вони НІКОЛИ не збігаються
   рядково, `--select "lv_path=..."` завжди повертав порожньо, скрипт
   одразу падав на `die "/ не на LVM LV..."` навіть на справжній
   LVM-системі. **Виправлено**: `lvs` сам приймає шлях до пристрою як
   позиційний аргумент і резолвить його сам — `--select` тут зайвий.
2. **`DISK=$(lsblk -no PKNAME "$LUKS_PART")` без `-d`** — без цього
   прапорця lsblk показує весь ланцюжок нащадків (partition → cryptroot
   → LV), і в `$DISK` потрапляв багаторядковий сміттєвий рядок замість
   `nvme0n1`, що зламало б усі подальші команди (`sgdisk --backup=...
   /dev/$DISK` тощо). **Виправлено**: додано `-d`.

Обидва фікси перевірені наживо на реально змонтованому цільовому LVM
(`ubuntu-vg/ubuntu-lv`, `/dev/nvme0n1p3`) під час restore — коректно
повертають `VG_NAME=ubuntu-vg LV_NAME=ubuntu-lv` і `DISK=nvme0n1`.

Додатково: `LC_ALL=C` додано до `vgs`/`lvs` при парсингу розмірів
(захист від локалі з комою замість крапки в дробових числах).

**Підтверджено, що дедуплікація вже коректно спроектована** (не треба
писати додаткову "інкрементну" логіку): `restic backup` автоматично
шукає snapshot-батька за (hostname, шлях) серед УСІХ попередніх
snapshot'ів — і оскільки `SNAP_MOUNT=/mnt/root-backup-snapshot` той
самий шлях, що використовувався і в ОРИГІНАЛЬНОМУ ручному бекапі 2026-
09-08 (видно з `restore-system.sh`: rsync бере
`$MNT_RESTORE/mnt/root-backup-snapshot/`), майбутні прогони
`backup-system.sh` автоматично зв'яжуться з тим самим ланцюжком
snapshot'ів і завантажать лише зміни. Навіть якби parent не знайшовся
(інша hostname тощо), контент-адресоване сховище restic все одно НЕ
завантажить повторно вже наявні за хешем блоки — просто без прискорення
"пропустити незмінені файли за mtime".

`bash -n` + `shellcheck -S warning` на `backup-system.sh` — чисто.
**Ще не запускався на реальній встановленій системі** (бо restore ще

## КРИТИЧНИЙ інцидент: restore_root впав через переповнення Live-оверлею (2026-09-17)

Після ~49 хвилин `restic restore` (275 GiB) впав з тисячами
"no space left on device" і "Fatal: 4213493 errors". Причина: проміжна
тека `$MNT_RESTORE=/mnt/restic-restore` фізично лежала на **overlay
Live-сесії** (`/cow`, змонтований як `overlay` на `/`), який на цій
машині обмежений **~63G** (не на цільовому диску, де 398G вільно!). Це
успадковано з ОРИГІНАЛЬНОЇ ручної процедури в `RECOVERY.md` (той самий
шлях `/mnt/restic-restore` без пояснення, де він фізично має бути) —
там, судячи з усього, або тестові дані були меншими, або overlay був
іншого розміру; на цій конкретній машині (125GiB RAM, live-оверлей
~63G) це фізично не могло вміститись.

**Негайні дії:** звільнив overlay (`sudo rm -rf /mnt/restic-restore`,
з 100% зайнято до 5% зайнято).

**Структурний фікс (з підтвердженням користувача — обрав варіант
"bind-mount для root, без staging"):**

- **root (275G, головна проблема):** замість `restic restore --target
  $MNT_RESTORE` + `rsync` + `rm -rf`, тепер бінд-монтуємо `$MNT_TARGET`
  напряму на `/mnt/root-backup-snapshot` (точний шлях, з яким робився
  оригінальний бекап), і `restic restore --target /` пише крізь цей
  бінд одразу на цільовий диск, **без проміжної копії взагалі**. Це і
  безпечніше (нуль ризику нестачі місця для staging), і швидше (один
  прохід запису замість двох). **Перевірено ізольованим тестом** на
  тимчасовому restic-репо (`/tmp/restic-bindmount-test`) — підтверджено,
  що restic дійсно відтворює повний абсолютний шлях, і завдяки біндингу
  запис прозоро потрапляє в ціль без подвійної вкладеності; після
  `umount` оригінальний каталог на Live-сесії лишається неушкодженим.
- **boot (кілька сотень MB, не проблема за обсягом):** лишив
  staging-підхід (restic restore → rsync), але переніс `$MNT_RESTORE` з
  overlay на диск бекапу (`$SCRIPT_DIR/.restic-restore-tmp`, 558G
  вільно) — про всяк випадок, і додав перевірку місця наперед.
- **Нова функція `require_free_space_gib`** — перевіряє вільне місце
  ДО запису (а не постфактум по хмарі помилок): викликається перед
  root-restore (`$RESTORE_SIZE_GIB` на `$MNT_TARGET`) і перед
  boot-staging (3G на `$SCRIPT_DIR`). Перевірено вручну на реальних
  шляхах (397G на `/mnt/target`, 558G на диску бекапу — обидва OK; і
  що коректно падає при завищеній вимозі).
- Додано захисне розмонтування `/mnt/root-backup-snapshot` у
  `cleanup()`-trap (на випадок Ctrl+C точно між mount --bind і umount).

`bash -n` + `shellcheck -S warning` — чисто. Крок `restore_root` НЕ
позначений виконаним (журнал коректно змусить повторити саме цей крок,
попередні — wipe/LUKS/LVM/format/mount — залишаться пропущеними).

**Наступний запуск** повторить `restore_root` (тепер через bind-mount,
без ризику переповнення) і піде далі. Очікувано знову займе ~40-50 хв
на 275 GiB.

## Баг у власному коді кешування: set -e вбиває скрипт МОВЧКИ (2026-09-17)

Після фіксу bind-mount скрипт почав падати одразу після підтвердження
`yes` (розбіжність root/boot snapshot у часі), з кодом 1, БЕЗ жодного
видимого повідомлення про причину, і `CURRENT_STEP` лишався порожнім.

**Корінна причина:** `CACHED_FOR=$(cache_get restore_size_for_snapshot)`
— голе присвоєння з command substitution. Коли `.restore-cache` ще не
існує, `cache_get` повертає `[[ -f ... ]]` = false = exit 1. Під
`set -e` ГОЛЕ присвоєння `VAR=$(cmd)` (не всередині `if`/`||`/`&&`)
з ненульовим кодом команди **вбиває скрипт негайно**, ще до будь-якого
виводу — навіть якщо самій логіці подальше значення "не потрібне" як
умова (`-n "$VAR"` перевірка йде рядком нижче, але до неї просто не
доходить). Підтверджено мінімальною репродукцією
(`bash -c 'set -e; f(){ false; }; V=$(f); echo NEVER PRINTED'`).

**Виправлено в джерелі:** `cache_get()` тепер завжди `; true` в кінці
— завжди повертає 0 незалежно від того, знайдено ключ чи ні (порожній
вивід і так сигналізує "не знайдено", виклики перевіряють `-n "$VAR"`).
Заодно виправлено ДВА такі самі приховані бомби того самого класу, які
чекали свого моменту (ще не спрацьовували, але могли б мовчки вбити
скрипт замість показу людяного `die()`):
- `ESP_UUID`/`BOOT_UUID`/`ROOT_UUID=$(grep ... | grep -oP ...)` —
  додано `|| true`, щоб при порожньому результаті дійшло до вже
  написаного `die "Не вдалося прочитати UUID з blkid.txt"`, а не тихо
  вмерло рядком раніше.
- `MODEL`/`SERIAL=$(udevadm ... | grep ... | cut ...)` — додано
  `|| true` (диск без цих udev-властивостей — не привід валити весь
  скрипт, просто лишити поле порожнім).

Перевірено репродукцією "до/після" — підтверджено, що виправлений
`cache_get` більше не вбиває скрипт. `bash -n` + `shellcheck` чисто.

**За проханням користувача одразу після цього:** прибрано весь кеш —
`.restore-cache` (уже не існував) і власний restic-кеш метаданих
(`/root/.cache/restic` — там і жив реальний кеш, бо restore-system.sh
запускається через `sudo` без `-E`, тому `$HOME=/root`; а
`/home/ubuntu/.cache/restic` — залишок від ручних діагностичних
restic-команд без sudo під час сесії). Обидва видалено, журнал
`.restore-progress` не чіпали (6 кроків лишаються пройденими).

## Баг: efibootmgr падає в chroot — "EFI variables are not supported"

`update-initramfs`/`grub-install`/`update-grub` відпрацювали успішно,
але `efibootmgr -v` всередині chroot впав: "EFI variables are not
supported on this system" (код 2, `bash -eux` в heredoc це одразу
підхопив і вбив весь chroot-блок).

**Причина:** `/sys/firmware/efi/efivars` — ОКРЕМА змонтована файлова
система (`efivarfs`), яку звичайний `mount --bind /sys` НЕ підхоплює
(non-recursive bind не тягне вкладені монтування). Класична грабля
chroot-відновлення UEFI-систем.

**Виправлено:** додано окремий `mount --bind
/sys/firmware/efi/efivars "$MNT_TARGET/sys/firmware/efi/efivars"`
(з перевіркою `-d /sys/firmware/efi/efivars` про всяк випадок, і
ідемпотентним `findmnt` guard) одразу після основного циклу
bind-монтувань у кроці `chroot_grub`. Відповідно додано в unmount-цикл
(крок 12) — efivars розмонтовується ПЕРЕД `/sys` (нащадок перед
батьком), інакше `umount /sys` не спрацює, поки щось усередині
змонтоване.

Перевірено вживу: `findmnt /sys/firmware/efi/efivars` на Live-сесії
підтвердив, що efivarfs дійсно змонтований і доступний, просто не був
прокинутий у chroot. `bash -n` + `shellcheck` чисто. Chroot bind-мounти
(`/dev`, `/proc`, `/sys`, `/run`) з попередньої спроби лишились
змонтованими під `/mnt/target` — ідемпотентні `findmnt`-перевірки в
циклі коректно їх пропустять, додасться лише відсутній `efivars`.

1. Якщо система завантажилась — попросити користувача підтвердити
   (`findmnt`, `lsblk -f`, `vgs`, `lvs` мають виглядати як звичайна

2. Протестувати `backup-system.sh` на вже встановленій системі

   Скрипт уже пройшов ретельний аудит і має два виправлені реальні
   баги (визначення VG/LV, `lsblk -no PKNAME` без `-d`) — але жодного
   разу не запускався на справжній встановленій системі, тому
   `--dry-run` перед реальним запуском обов'язковий.
3. Якщо НЕ завантажилась — це новий інцидент, потрібна повна

   перевірити `efibootmgr -v` результат з логу chroot_grub — там мало

## Перший boot упав у BusyBox без запиту LUKS-пароля (2026-09-17)

Після формально успішного restore машина не показала запит LUKS-пароля і
впала в initramfs BusyBox. Діагностика з Live USB підтвердила:

- LUKS header і пароль справні, UUID контейнера
  `cdcf5dac-5567-40ab-ab15-87c57c480f33` збігався з `/etc/crypttab`;
- root LV, `/boot`, ESP, `fstab` і GRUB `root=` були коректні;
- cryptsetup та LVM-бінарники/скрипти були в initramfs;
- але файл `main/cryptroot/crypttab` усередині обох initramfs був
  **порожній**.

Причина: `update-initramfs` у chroot завершився з кодом 0, але автоматичне
визначення encrypted root не спрацювало в оточенні Live-системи. Після
явного запису
`cryptroot UUID=<LUKS_UUID> none luks,initramfs` і повторного
`update-initramfs -u -k all` embedded crypttab заповнився, запит пароля
з'явився і система успішно завантажилася.

`restore-system.sh` допрацьовано: він формує цей запис із UUID фактичного
цільового LUKS header, інвалідує старий `chroot_grub`, а після генерації
розпаковує кожен версійний initramfs і завершується помилкою, якщо embedded
`cryptroot/crypttab` порожній або не містить правильного UUID.
